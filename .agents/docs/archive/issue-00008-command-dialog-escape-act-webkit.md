# `CommandDialog` Escape with text in the input logs `act` errors in WebKit

## Escape on a `CommandDialog` whose input has a query fails the WebKit story gate

- status: resolved (2026-11-25)
  area: frontend/uilibs
  summary: In WebKit, pressing Escape in `CommandDialog` (`packages/uilibs/src/extra/command/command.component.tsx:53`, built on Base UI `Autocomplete` in `inline open` mode, `:35`) while the input still held a query logged 8 console errors, "An update to %s inside a test was not wrapped in act(...)" plus "A component suspended inside an `act` scope, but the `act` call was not awaited". `.storybook/preview.tsx:168-170` throws on any console error, so the story failed with "The story logged 8 console error(s)". Reproduced 2026-11-25 by removing the `userEvent.clear(input)` step before Escape in the `Keyboard` play: WebKit 1 failed, 6 passed; Chromium 7 of 7. Chromium and Firefox close the dialog on one Escape and the input keeps its text (`potions`).
  cause: found 2026-11-25 with a throwaway story in all three engines (deleted). On close, Base UI 1.9.0 runs a WebKit-only layout effect that calls `blur()` on the focused input inside the popup, so Safari does not scroll the page when a focused input unmounts (`@base-ui/react/floating-ui-react/components/FloatingFocusManager.mjs:547-561`, behind `platform.engine.webkit`). The blur event fires synchronously inside React's commit, and `ComboboxInput`'s `onBlur` (`combobox/input/ComboboxInput.mjs:167-176`) calls `setIndices({ activeIndex: null })` for an `inline` Combobox with a highlighted item, which re-renders the item, the root and the list. React reports it because Storybook's test renderer wraps `userEvent` dispatches in an `act` scope (`@storybook/react` `eventWrapper`). With the same Escape sent as a plain `KeyboardEvent`, the `blur()` and the updates still run in WebKit and nothing is logged. The update needs both a query and a highlighted item (errors raised during `blur()`: `potions` 3, `o` 2, empty query 0, no match 0). Production has no `act`. In WebKit without the wrapper, one Escape with text closes the dialog, focus returns to the trigger, and reopening gives an empty input with a working highlight, as in Chromium. Not a component defect and nothing a user sees; `@base-ui/react` 1.9.0 is the latest release, so an upgrade changes nothing.
  resolution: the owner kept Escape closing at once (no clear-first step) and the `Keyboard` play sends that one Escape natively. `command.stories.tsx` drops the `userEvent.clear` workaround, asserts the input still holds `potions`, and dispatches `new KeyboardEvent('keydown', { key: 'Escape', bubbles: true })` on the input inside a `waitFor` until the dialog is gone (a repeat is safe, and WebKit can lose a key sent while the dialog settles). The play now proves Escape closes a palette that holds a query: `command.stories.tsx` passes in Chromium, Firefox and WebKit, light and dark. `command.mdx` says Escape closes the dialog whatever the input holds. The rejected options: a per-story `act` allowlist in the gate (hides real `act` problems), keeping the workaround (proves nothing about a query), and a component change that mutes Base UI's blur (changes behavior to quiet a test-only warning).
  trigger: None. Closed. If a later Base UI release stops blurring in the commit, the native dispatch can go back to `userEvent`.
